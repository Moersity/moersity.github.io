推理服务开始收缩故障域：坏请求、断链与半成品缓存不再拖垮进程

最近 48 小时最值得关注的不是新版本，而是 vLLM 与 SGLang 同时把输入校验、传输失败和缓存发布从引擎级故障降为请求级失败。

01

今日最重要

  1. vLLM 在调度前校验 Cache Salt，堵住单请求终止 LMCache-MP 引擎的路径 — vLLM 过去接受任意非空 Cache Salt，而 LMCache 会拒绝包含 @、斜杠、反斜杠、NUL 或超过 128 字符的值；异常抵达共享 Engine Core 后会被当成致命错误。新校验覆盖 Completions、Chat、Responses、Pooling 与 Scale-out 请求，在进入 Scheduler 前返回客户端错误。判断：跨组件输入约束必须由最外层采用下游最严格规则；否则一次可预见的 4xx 会升级为共享进程故障和多租户中断。
    vLLM PR #51444
  2. SGLang EPD Receiver 增加消息、布局、所有权校验与有界等待 — 接收端现在会在重建 Feature 前验证消息、Shape、Dtype、Count 与 Request Ownership；取消或陈旧 Receive 会释放资源，Malformed、Duplicate、Timeout 或 Disconnect 只失败当前请求，Receiver Loop 继续服务后续请求。判断：E/P/D 边界本质是分布式协议边界，必须像公网入口一样验证长度、布局、身份和生命周期，并保证解析失败不会终止长期运行的接收循环。
    SGLang PR #36945
  3. SGLang 把 Encoder Cache 发布改为事务式提交 — 本地 Embedding Cache 与全局 Mooncake Cache 的 Staging、Publication 和 Cleanup 被统一为全有或全无；部分 Feature 发布、取消或传输失败会回滚，Optional Global Cache 故障则退化为当前请求的 Cache Miss。判断：缓存是优化而非正确性依赖。可见状态必须在完整工件准备好后一次发布，任何半成品都应不可命中，并能按 Request ID 幂等清理。
    SGLang PR #36949
  4. vLLM NIXL 重复失败清理不再触发 Engine-wide Assert — 一个请求跨多个 Remote Rank 拉取 KV 时，各 Transfer Handle 可能在不同 Poll 失败并重复上报同一 Request ID。旧路径第二次清理会触发 Worker 与 Scheduler 断言；新逻辑忽略已清理 Metadata，并阻止重复完成事件进入 Scheduler，使故障只影响原请求。判断：分布式清理必须按至少一次通知设计。完成、失败、取消和超时事件都应幂等，重复到达不能进入会终止进程的 Assert。
    vLLM PR #54518
  5. vLLM 用 Prefill Token Budget 限制多模态 Renderer Warmup 的 CPU 内存 — 长上下文多模态 Warmup 曾构造并保留不必要的完整上下文 Dummy Input；启用 Chunked Prefill 时，新路径按 Scheduler 的 max_num_batched_tokens 限制 Renderer Warmup，其他 Profiling Caller 仍保留完整上下文行为。判断：Warmup 应复现实际单步执行上限，而不是模型理论最大上下文；否则为避免冷启动抖动而引入的预热本身会成为内存峰值。
    vLLM PR #55448
02

AI 推理 / 系统工程动态

最近 24–48 小时没有值得单列的 vLLM 或 SGLang 稳定版，主干变化集中在失败边界。除 Cache Salt、NIXL 和 EPD 修复外，SGLang 把过小 SWA Pool 从 600 秒 Warmup 卡死改成启动期 ValueError，并明确给出 Sliding Window 加 Page Size 的最低 Headroom；vLLM 则让 EAGLE3、DFlash 与 DSpark 外部 Draft Model 在显式支持的 Target Model 上跨 Pipeline Stage 转发辅助 Hidden State，并保持 Full CUDA Graph 路径。

判断：生产推理的核心指标不只是成功请求延迟，还包括错误隔离半径、失败检测时间和回滚完整性。建议把引擎存活、请求级降级和残留状态纳入每个 Connector 与 Cache 的验收。

03

后端与云原生 / Rust / Golang 动态

Kueue 修复两类容易制造幽灵容量或调度漂移的状态问题：当多 PodSet Workload 的某个 PodSet 已全部可回收时，Topology Assignment 会与 Quota 一起释放，避免已停止部分长期占用故障域；Kubeflow Trainer 的 TrainJob Admission 则保留 TrainingRuntime 与用户 Runtime Patch 中的 Toleration，再按 Kubernetes Identity 合并 ResourceFlavor Toleration。最近 24–48 小时没有新的 KServe 高价值变更，也没有需要单列的 Go 或 Rust 稳定版。

判断：配额释放、拓扑释放与 PodSpec Patch 必须保持原子一致；只释放 Quota 不释放 Topology，或用原子列表覆盖用户 Toleration，都会让控制面状态与实际可调度容量分叉。

04

值得看的项目 / 论文 / 工具

  1. SGLang EPD 故障隔离双补丁 — Receiver Hardening 负责入口验证、有界等待和资源释放；Transactional Publication 负责本地与 Mooncake Cache 的完整提交、回滚和请求级降级。判断：两者应作为一个故障注入矩阵验收，覆盖缺包、乱序、重复、断链、取消、部分发布和缓存控制器异常。
    Receiver ValidationTransactional Publication
  2. SGLang UMBP External Linker — 新增 Mori Direct Linker、Layer-wise 与 Grouped Ranged I/O、Batched Offload、GPU Buffer Registration，以及可由多个 Worker 共享的 Standalone Host Pool；对象 Key 也加入 Backend Tag 与 Model Name。判断：硬件验证显示路径已贯通，但 Direct Linker 依赖尚未合入且未被官方镜像固定的 ROCm/mori #540；当前应视为可评估主干能力，而不是开箱可用功能。
    SGLang PR #37578ROCm Mori PR #540
  3. SGLang Load-aware Prefill Admission — Router 为 Session-aware 与 Cache-aware Policy 引入有界 Prefill Proposal，并统一经过 Eligibility、Capacity 与确定性主备回退；陈旧或缺失的 Engine Load Snapshot 会回退到 Router 本地在途量。判断：这是比单纯 Least-load 更稳健的控制面骨架，但 PR 没有 GPU E2E 性能结论；应先验证新鲜度阈值、回退稳定性和 Proposal 上限。
    SGLang PR #37843
  4. vLLM EAGLE3 Pipeline Parallel — 辅助 Hidden State 通过既有 IntermediateTensors 按全局 Layer 顺序跨 PP Stage 传递，Draft Model 只在最后 Stage 运行，Proposal 再广播给前序 Stage。判断：适合评估跨节点推测解码，但只应在 Target Model 显式支持辅助状态转发时启用，并分别验证 Eager、Full Graph 和 Piecewise Graph。
    vLLM PR #50514
05

产业趋势与投资信号

最近 24–48 小时未核验到足够重大且有公司一手公告支持的推理基础设施融资或并购。更可靠的产业信号是故障隔离成为框架共同投入方向：输入约束前移、Receiver 长驻、缓存事务发布、清理幂等和启动 Fail-fast 都在把共享引擎从单点崩溃模型改造成请求级降级模型。

判断：多租户推理平台的商业价值越来越取决于 Blast Radius，而不只是峰值 Tokens/s。采购与自研指标应加入单坏请求影响数、Connector 断链恢复时间、缓存残留率和引擎存活率。

06

行动建议

  1. 把 Cache Salt、Connector 参数和多模态元数据的下游约束复制到最外层 Admission，并用非法字符、超长值和跨接口一致性测试验证 4xx 行为。
  2. 对 KV 与 Encoder Transfer 注入多 Rank 分时失败、重复完成、取消和断链，要求只失败原请求且 Engine Process 持续存活。
  3. 为缓存发布实现 Staging、Commit、Rollback 三阶段，并在每个阶段注入异常，确认任何部分对象都不可被后续请求命中。
  4. 为 Warmup 设置与 Scheduler 单步预算一致的 Token、Media 和 CPU Memory 上限，同时保留独立的完整上下文 Profiling 模式。
  5. 在启动前验证 SWA Pool、Page Size 与 Sliding Window 的最低 Headroom，禁止依赖 Watchdog 发现永不前进的 Admission Loop。
  6. 为 Kueue 多 PodSet Workload 核对 Quota 与 Topology 的同步释放，并验证 Admission Patch 不覆盖用户或 Runtime 已声明的 Toleration。
