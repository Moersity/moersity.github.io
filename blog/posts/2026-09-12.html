多池调度的隐形偏置：SMG 修正候选集轮转，PD 失败语义开始统一

SMG 修复多个 P/D Cohort 共享 Round Robin 计数器造成的 Decode 饿死；SGLang 统一三种 KV 后端的失败通知，并补齐 DCP1→DCP-N 的 Draft KV 重排。

01

今日最重要

  1. SMG 将 Round Robin 轮转状态按候选集合隔离 — 协议感知 P/D 配对后，同一个 Decode Policy 会交替收到不同 Cohort 的候选列表；旧实现共用一个计数器，列表交错与取模会产生别名，使两个 1P2D Cohort 中各有一个 Decode 永远收不到流量。新实现按有序健康 URL 集合保存独立轮转，集合上限 4096 并以 LRU 淘汰；复现测试从 60/0、0/60 恢复为每个 Decode 30 个请求。判断：任何会在动态子集上运行的有状态策略，都不能默认候选空间恒定。轮转、哈希和缓存亲和策略应明确状态键，并测试多个集合交错、扩缩容和重注册。
    SMG PR #2507
  2. SGLang 统一 NIXL、Mooncake 与 Mori 的 P→D 失败通知 — NIXL 过去没有 Prefill→Decode 失败通知，Broken Transfer 只能等默认 300 秒超时；Mooncake 与 Mori 则各自维护状态机。新路径把首个根因、终态、目标解析和 Decode 聚合收进 CommonKVManager，并为 NIXL 增加 KV_STATUS 通知，修复失败被后续状态覆盖、已清理 Room 被重建和失败 Room 跟踪泄漏等问题。判断：KV 数据面可以因后端不同而优化，但失败语义必须一致。该 PR 仍明确缺少 NIXL 多 Rank 与 Mori AMD 的 GPU 故障注入验证，上线前应补齐端到端快速失败测试。
    SGLang PR #36612
  3. vLLM V2 为 Pipeline Parallelism 补齐 MTP 推测解码 — vLLM 修复 MTP Drafter 未声明 SupportsPP、Qwen3.5/3.6 Draft Head 跳过 FC、DeepSeek 系列未加载自身 Embedding、Sparse MLA 读取陈旧 TopK Buffer，以及后续 PP Rank 缺少 Encoder Runner 等一组耦合问题。PR 在 Qwen3.5/3.6 与 GLM-5.2 的 PP=2 配置上报告了约 80%–95% 的 Token Acceptance，具体取决于模型与推测步数。判断：推测解码叠加 PP 时，正确性不能只用最终输出验证：未初始化权重或陈旧 Buffer 可能被拒绝机制掩盖，应把 Draft Acceptance、各 Stage 权重归属和异步 Stream 生命周期纳入验收。
    vLLM PR #46994
  4. SGLang 支持 DCP1 Prefill 向 DCP-N Decode 传输 DSPARK Draft KV — Decode 现在发布按 P×N Token 组织的虚拟页，Target KV 按 Owner 每 N 个 Token 取一项并打包，Draft KV 则保留完整序列；Mooncake 与 NIXL 从同一 Transfer Plan 发送两部分。当前覆盖 Kimi-Linear TP4、DCP1→DCP4，明确不包含 DCP>1 Prefill 和异构 P/D TP×DSPARK。判断：DCP 重排必须把 Target 与 Draft 的所有权规则建模成同一个可验证计划，而不是分散在 Connector 中。下一步重点是异构 TP 组合与长上下文下的 Buffer 峰值。
    SGLang PR #37709
  5. SGLang 规避 Pure-DP Decode 在突发流量下的 NCCL Graph 死锁 — TP LM-head All-to-all 被捕获进 Decode CUDA Graph 后，Pure-DP 各 Rank 从空闲状态以不同速率接入新请求，可能在首轮突发中让部分 Rank 卡在 ncclDevKernel_SendRecv。新实现仅在该 All-to-all 路径自动设置 NCCL_GRAPH_REGISTER=0，并保留用户显式配置；PR 的 TP4/DP4/EP4 复现中由每次首轮挂死改善为 10 轮突发全部完成。判断：这是并发相位差而非数值精度问题。复测要从空闲开始制造不对称 Admission，并监控各 Rank Step、Graph Replay 和 Collective 进度；PR 对 NCCL 内部机制的解释仍是基于实验矩阵的推断。
    SGLang PR #38936
02

AI 推理 / 系统工程动态

SMG 还为 Kimi 与 MiniMax 增加 Provider Extension Module：通过 Serde Flatten 保留 Kimi 系统消息动态 Tools、MiniMax 图片/视频参数，并允许省略 System Content；官方 Vendor Verifier 子集的动态工具用例从 46/72 提升到 68/72，仍有四个角色级拒绝规则留待 Profile Validation。项目最近 24–48 小时没有新 Release，最新仍为 v1.10.1。重要未决风险有两项：Worker Groups / Serving Sets 设计正在解决不同形状或速度 Cohort 只按 Prefill 侧分流的问题；SGLang+NIXL 的 Decode 同地址重启仍可能令 Prefill 在 add_remote_agent 中崩溃，相关重启测试暂时被排除。

判断：SMG 已从协议兼容推进到多 Cohort 公平性，但 Worker 内公平不等于 Cohort 间负载均衡。应把 Serving Set 的最慢 Leg 成本、每组流量和重启失败率作为下一阶段核心指标；Provider 扩展则应继续放在显式模块中，避免核心 OpenAI Schema 无边界膨胀。

03

后端与云原生 / Rust / Golang 动态

KServe 的 LLMInferenceService 新增 runtime 字段，可在 vLLM 与 SGLang 之间选择，默认仍为 vLLM，并提供独立 SGLang 模板与示例。Kueue 为 WaitForPodsReady 增加 Unscheduled Pods Tracker，把 Pod 调度进度写回 Workload 的 PodsScheduled，并与 WaitForScheduling 原因传播衔接。vLLM Rust Frontend 也修正 gRPC 错误语义：Engine 生成失败现在返回 INTERNAL，流式请求保留已发送内容后以错误终止，客户端主动取消不变。最近 24–48 小时 Go、Rust 与 Kubernetes 官方发布列表均无新稳定版本。

判断：推理平台的 Runtime 抽象正在进入 Kubernetes API，但可替换不应只验证模板选择，还要覆盖探针、指标、伸缩和错误语义。调度侧则应把已准入、已调度和已就绪拆成独立状态，才能安全回收被未调度 Pod 占用的配额。

04

值得看的项目 / 论文 / 工具

  1. 动态候选集 Round Robin 的状态键设计 — SMG 用有序健康 URL 集合标识 Rotation，并设计容量上限、共享 Seed、Miss 驱动的 LRU 与 Reset 语义。判断：适合作为动态 Worker Pool 策略单测模板，尤其要复现两个集合交错导致的取模别名，而不只测单集合均匀性。
    SMG PR #2507
  2. Worker Groups 与 Serving Sets 设计草案 — SMG 提议以协议兼容的 Leg Group 组合成 Serving Set，再用各组最佳 Worker 预计等待时间的最大值衡量整套服务成本。判断：它抓住了 PD 系统的关键：瓶颈由最慢 Leg 决定。当前仍是 Open Issue，应重点评审 Affinity Policy、共享 Decode Group 和缺失 Load Report 的退化行为。
    SMG Issue #2508
  3. vLLM Disk KV Offload 的对齐边界 — Disk Backend 过去无条件要求每 Block 字节数按 4096 对齐；修复后只在 O_DIRECT 路径强制，使用 Page Cache 的 Buffered I/O 可接受非 4096 对齐的 Hybrid KV Layout。判断：所有对齐断言都应绑定实际 I/O 模式；建议分别用 Direct 与 Buffered 路径验证 Offset、Length、Buffer Address 和文件最终尺寸。
    vLLM PR #55424
  4. vLLM 小 Batch FP8 MLA Cache 写入合并 — vLLM 把五层独立 KV Cache 插入合并成一次 Grouped Kernel Launch；PR 微基准在 1–2048 Token 多数点报告约 4–7 倍 Kernel 级加速，8K 以上收益接近消失。判断：这是减少 Launch Tax 的清晰案例，但尚无端到端吞吐数据；评估时应按实际 Decode Batch 分布加权，避免把小 Batch 微基准外推到整机收益。
    vLLM PR #55356
05

产业趋势与投资信号

最近 24–48 小时未核验到足够重大、且有公司一手公告支持的推理基础设施融资或并购。工程侧信号更值得关注：多 Runtime、分离式 P/D 与多 Cohort Rollout 已把网关问题从单池负载均衡推向“兼容集合 × 多阶段瓶颈 × 一致失败语义”的联合控制。

判断：采购或自研推理网关时，应要求展示异构 Cohort 灰度、某一 Leg 变慢、传输失败和 Worker 同址重启四种场景，而不是只看稳态均匀流量；能否在错误发生前隔离兼容域、发生后快速释放资源，正在成为平台分水岭。

行动建议

  1. 在 SMG 预发环境构造两个 1P2D Cohort 交错请求，确认每个 Decode 均匀接流，并补测候选集缩容、扩容和同 URL 重注册。
  2. 对 1P2D 与 3P2D 混合 Rollout 注入 Decode 降速，记录每个 Cohort 的 Prefill/Decode 排队时间，为 Serving Set 最慢 Leg 评分建立基线。
  3. 在 NIXL、Mooncake、Mori 上统一注入 Prefill 传输失败，验证 Decode 快速收到根因、Room 只清理一次且 Bootstrap Room ID 复用不继承旧错误。
  4. 复现 SMG Issue #2503 的 SGLang+NIXL 同址重启崩溃；修复前不要把相关重启测试从跳过列表移回发布门禁，也不要把该组合标为完全恢复安全。
  5. 为 MTP+PP 验收增加 Draft Acceptance 告警与各 Stage 权重加载审计，避免最终输出正确掩盖推测路径失效。
  6. 试用 KServe 的 SGLang Runtime 时，同时验证 Readiness、Prometheus 指标、Autoscaling、错误码和升级回滚，不以 Pod 成功启动作为完成标准。
