推理系统技术日报 · 2026-08-29

推理系统的下一轮收益，来自把数据移动藏进计算窗口

vLLM 把远端 KV 提交后移以覆盖 GPU 计算，SGLang 修复分层缓存的跨流与租户隔离风险，KServe 则补上 P/D 拓扑中真正执行 KV 传输的连接器。

01

今日最重要

  1. vLLM 将异步 KV 拉取与 GPU Forward 重叠 — 主干在没有同步 KV Load 的步骤中，把 NIXL 的 start_load_kv 从 pre_forward 延后到当前 Forward 已发射之后，使远端描述符构造与提交可被 GPU 计算覆盖；该改动面向扩展型 P/D 部署，尚未进入新的稳定版。判断：这类优化的核心指标不是单点 TTFT，而是 TPOT、尾延迟和传输队列的联合变化；应按同步与异步命中比例分桶验证。
    vLLM PR #53333
  2. SGLang HiCache 补上跨 CUDA Stream 的写入屏障 — Overlap Scheduling 可能在旧请求仍写 KV 页时回收并复用页面，而 HiCache 的 H2D Load-back 位于独立传输流；新修复让传输流等待 Forward Stream，避免旧写入覆盖恢复的 Prefix。判断：分层 KV Cache 的正确性边界已经从 Key 和生命周期扩展到 Stream Ordering；仅靠 Page Allocator 的所有权检查不够。
    SGLang PR #36738
  3. SGLang 修复多租户 Prefix 预取的 Namespace 错配 — L3 Storage Prefetch 过去从 Anchor Node 而非请求本身派生 extra_key/cache_salt，非默认命名空间可能把数据写入错误 Key，并在后续重新归属时发生重复释放。修复改用请求命名空间并加入回归覆盖。判断：Cache Salt 不是附加标签，而是缓存身份的一部分；查找、预取、插入、驱逐和释放必须共享同一 Canonical Key。
    SGLang PR #36382
  4. KServe 为 P/D Engine 注入 NixlConnector — LLMInferenceService 的 Prefill/Decode 模板此前生成了分离拓扑，却没有配置实际传输 KV 的 Connector。合入修复为两类 Engine 注入 NixlConnector，避免拓扑存在但 KV 没有传输。判断：控制面不应只验证角色与 Pod 是否存在，还要验证数据路径可达；P/D Ready 条件应覆盖 Connector、传输端点与一次真实 KV 握手。
    KServe PR #6027
  5. vLLM 修复 NCCL 2.31 结构体版本导致的堆越界 — vLLM 的 ctypes 结构仍按 NCCL 2.30 的 56 字节布局，却向 ncclCommQueryProperties 声明运行时 2.31 版本，后者可能写入更大的结构并导致多节点 Expert Parallel 场景出现随机 SIGSEGV；修复改为声明编译期 Header 版本。判断：这是 ABI 边界问题，不是普通 Python Bug。升级 NCCL 时必须把 ctypes/CFFI 结构尺寸、Header 版本和 Runtime 版本的组合纳入启动自检。
    vLLM PR #53008
02

AI 推理 / 系统工程动态

最近 24 小时没有新的 vLLM 或 SGLang 稳定版；高价值变化均位于主干。vLLM 通过调整异步 KV 提交时机来隐藏 Host-side 工作，SGLang 同时补齐 HiCache 的跨流排序和租户命名空间一致性，并加入面向 AMD 长上下文低批量 Decode 的 Work-Centric Persistent-CTA Attention。共同主题是：吞吐收益越来越依赖传输、计算、缓存身份和并发时序能否被统一调度。

判断：生产验证要从单 Kernel Benchmark 升级为数据路径 Timeline：记录 Forward、KV Pull、H2D、Page Reuse、Prefix Lookup 和 Stream Fence，并按租户与请求 Namespace 关联。

03

后端与云原生 / Rust / Golang 动态

Kueue 合入 PartialScaleUp for ElasticJobs 的 KEP，允许弹性工作负载在完整配额不足时按组件最小数量先启动、容量出现后再扩展；同时修复 Fair-sharing Preemption 只比较 LocalQueue 名称、忽略 Namespace 的问题。KServe 的 NixlConnector 修复则说明声明式拓扑仍需对实际数据面配置负责。最近 24–48 小时没有新的 Go 或 Rust 稳定版本，因此不收录零散编译器提交。

判断：弹性准入会提高碎片资源利用率，但也会改变启动时间、Gang 语义和公平性；上线前应以 Namespace-qualified Queue 身份重放真实配额与抢占轨迹。

04

值得看的项目 / 论文 / 工具

  1. SGLang Work-Centric Attention — 为 AMD 长上下文、低 Batch Decode 引入 Persistent-CTA Kernel，让工作单元动态领取 KV Tile，减少固定 SplitK 在低占用场景中的空闲 CU。判断：适合用真实上下文长度分布测试；不要把特定 AMD 平台的 Kernel 收益外推到所有硬件与 Batch 区间。
    SGLang PR #33576
  2. vLLM Rust Frontend SSE Hot Path — 把每个流式 Chunk 都重复创建的不变响应 Envelope 改为单次共享，并直接序列化进 SSE Buffer，减少临时 JSON String 与整段复制。判断：这是典型的按 Token 放大成本；应同时比较 CPU/Token、Allocation/Chunk、首包延迟和高并发尾延迟。
    vLLM PR #51321
  3. Kueue PartialScaleUp KEP — 定义弹性 Job 的最小组件规模、部分准入与后续扩容方向，目标是在完整配额暂不可用时先利用可用容量。判断：值得为 Ray 等弹性负载预演，但 KEP 合入不等于功能已发布；需继续跟踪实现、Feature Gate 与版本落点。
    Kueue PR #14310
  4. vLLM NCCL ABI 修复说明 — PR 清楚展示运行时版本、编译期 Header 与 ctypes 结构布局不一致如何造成 Heap Corruption，并给出多节点 Expert Parallel 的触发背景。判断：可直接转化为原生库绑定审计清单：结构尺寸、版本字段、动态库来源和兼容矩阵必须可观测。
    vLLM PR #53008
05

产业趋势与投资信号

最近 24–48 小时未核验到足够重大、且有公司一手公告支持的推理基础设施融资或并购。更可信的产业信号来自主干工程：vLLM、SGLang 与 KServe 都在把 P/D、远端 KV、分层缓存和流式协议从概念能力推进到可验证的数据路径；Kueue 则尝试让弹性作业更充分地消费零散集群配额。

判断：下一阶段平台差异不会只体现在单卡 Tokens/s，而在于能否把跨节点 KV、Host 开销与弹性配额安全地藏进计算窗口，同时维持多租户隔离和可诊断性。

06

行动建议

  1. 在 P/D 压测中分别记录 KV 提交 Host Time、Forward Launch、TTFT、TPOT 与 P99，验证异步提交是否真正被 GPU 计算覆盖。
  2. 为分层 KV Cache 加入跨 Stream 数据完整性测试，并在 Page Free/Reuse/Load-back 事件中记录 CUDA Event 与 Request Namespace。
  3. 对 extra_key/cache_salt 做多租户并发预取、驱逐与重复释放回归，确保所有缓存层使用同一 Canonical Key。
  4. 为 KServe P/D Ready 条件补充 Connector 配置、端点连通与一次真实 KV 传输探针，避免仅凭 Pod Ready 放量。
  5. 在 NCCL 升级门禁中校验 Header、Runtime、ctypes 结构尺寸与 Expert Parallel 多节点稳定性。
  6. 用历史 Ray/Kueue 轨迹模拟 PartialScaleUp，比较资源利用率、作业完成时间、公平性与抢占次数后再决定是否启用。
