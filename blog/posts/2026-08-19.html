KV Cache 成为移动状态，调度开始直接承载多档 SLA

今天最值得关注的是主动 KV 迁移与多级优先级调度：前者把移动性预测引入推理状态管理，后者把商业服务等级落实到 Headroom、迁移与尾延迟。

01

今日最重要

  1. Pallas 在蜂窝切换前主动准备 KV Cache — 系统将上下文拆成稳定 Prefix 与持续增长的 Suffix：目标站本地重算 Prefix，源站并行流式传输新增 KV，并根据移动性预测和运行时遥测选择预取窗口。论文的 vLLM 原型在三种模型和 100–500 Mbps 站间链路上报告，平均服务中断时间相对目标侧恢复缩短 2.28–89.68 倍。判断：KV Cache 已不只是显存优化对象，而是需要预测、复制、版本拼接和一致性交接的分布式状态。
    Pallas 论文
  2. 多级 SLA 调度显示四档优先级可能是甜点位 — 研究在 Vidur 中扩展 Llumnix，把二级优先级改为任意多档，并加入逐档 Headroom、指数衰减和迁移管线；仿真中四档在三种优先级分布下取得最佳成本—延迟折中，端到端 P99 相对 INFaaS 基线最高加速 3.1 倍。判断：优先级不是简单排序；真正的 SLA 隔离需要保留容量、迁移能力、分档遥测和明确的降级规则。
    多级 SLA 调度论文实验代码
  3. 迁移成为移动性与服务分级的共同底座 — Pallas 用迁移解决用户跨站移动，Llumnix 路线用在线迁移解决负载、碎片和优先级；两条路径都要求请求状态可定位、可搬运并能在目标实例快速恢复。判断：未来 Router 需要同时管理算力位置、KV 位置、迁移成本和业务等级，单一 Queue Length 已不足以做全局决策。
    PallasLlumnix
  4. 主流框架与语言近 48 小时无新正式版 — vLLM 最新正式版仍为 v0.27.1，SGLang 为 v0.5.17，Kubernetes 1.37 仍是 rc.0；Go 1.27 官方说明仍标注 DRAFT，Rust 也没有新的稳定版。判断：今天不重复旧版本新闻，应优先验证 KV 迁移与多租户 SLA 的工程边界。

02

AI 推理 / 系统工程动态

Pallas 的关键不是单纯更快地复制 KV，而是按时间依赖拆分状态：历史 Prefix 在目标侧提前 Prefill，动态 Suffix 从源侧持续追赶，再在切换点合并。多级 SLA 工作则把请求迁移、逐档 Headroom 和优先级分布放入同一调度器。二者都要求运行时掌握 KV 年龄、大小、位置、剩余传输量以及请求的延迟预算。

判断：KV 迁移 API 应暴露准备、追赶、冻结、拼接、恢复和回滚六个阶段；调度器则必须用收益减去迁移与预留成本，而不是看到高优先级就立即搬运。

03

后端与云原生 / Rust / Golang 动态

Kubernetes 1.37 最新仍为 rc.0，Go 1.27 页面仍是草案，Rust 近 48 小时没有新稳定版。控制面真正需要补强的是状态目录与遥测：实例、KV Segment、版本、传输进度、目标 SLA、剩余预算和失败原因都应可查询，并通过幂等状态机协调源端与目标端。

判断：Go/Rust 控制面要把迁移设计成可重试事务，而不是一组无状态 RPC；Kubernetes 上则应把迁移与 Pod 生命周期、抢占和拓扑变化关联起来。

04

值得看的项目 / 论文 / 工具

  1. Pallas: Proactive KV Cache Migration for AI-RAN — 给出 Prefix 重算、Suffix 流式追赶和预测式预取窗口的完整设计与 vLLM 原型。判断：即使不做 AI-RAN，也可借鉴到跨可用区迁移、节点维护和故障前排空。
    arXiv
  2. Beyond Binary Priorities — 在 Vidur 中复现迁移管线并评估 1–10 档 SLA、不同业务分布与逐档 Headroom。判断：适合作为商业分层上线前的离线实验模板，但仿真结果仍需真实集群回放验证。
    arXivGitHub
  3. Vidur 推理系统模拟器 — 支持在少量性能画像基础上，对模型、设备、流量和调度策略做大规模模拟。判断：可先筛掉明显不合理的 SLA 分档与容量方案，再把少数候选放进昂贵的 GPU 实验。
    Vidur GitHub
  4. Llumnix 动态请求迁移 — 以在线迁移统一负载均衡、碎片整理、优先级与自动扩缩容。判断：适合作为构建迁移状态机、Freeness 指标和多实例重调度的基础阅读。
    arXiv
05

产业趋势与投资信号

最近 24–48 小时未核验到足够重大且有一手公告支持的推理基础设施融资或并购。更明确的产业信号来自架构：移动边缘推理需要 KV 随用户迁移，商业 API 又需要多档 SLA 共享同一 GPU 池。这会提高对低时延互连、状态目录、迁移编排、容量模拟和按等级计费能力的需求。

判断：推理平台的商业价值将越来越取决于能否证明每档 SLA 的 P99、迁移成功率和单位请求成本，而不是只有全局平均吞吐。

06

行动建议

  1. 为现有推理服务建立 KV 状态目录：记录请求、Segment、版本、源/目标实例、字节数、传输进度和有效期。
  2. 实现迁移故障注入，覆盖目标节点失联、Suffix 落后、重复提交、源端退出和切换后回滚。
  3. 用真实业务 Trace 将请求划分为 3–5 档 SLA，测量逐档 TTFT、TPOT、P99、抢占率、迁移次数和 GPU 空置成本。
  4. 先在 Vidur 或等价模拟器中筛选 Headroom 与分档数量，再在小规模 GPU 集群回放验证。
  5. 继续把 Kubernetes 1.37 rc.0 与 Go 1.27 草案限制在隔离 CI，生产版本保持不变。
